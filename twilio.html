Twilio is the first API on this site whose core limit is concurrency, not rate. You are not sending too many requests per second — you have too many connections open at once. Waiting and retrying does not fix that.

Which throttle do you have?

Twilio's REST API is limited by concurrency, not requests per second. The default is roughly 100 simultaneous in-flight requests per account, raisable through Twilio Support. Exceeding it returns HTTP 429 with error code 20429. Separately, the Verify API limits each phone number to 5 sends and 5 checks per 10 minutes, and Twilsock (error 51202) caps new SDK connections at 110 per second per subaccount. All three return 429 — the error code tells you which.

The one that looks like an error but isn't. Sending more SMS per second than your sender allows does not return 429. Twilio accepts the message, queues it, and delivers at the sender's permitted rate. The 429 and the slow delivery are two different problems on two different axes.

REST API concurrency — the core limit

Twilio's core limit is approximately 100 simultaneous in-flight REST API requests per account, and the axis is in-flight requests, not requests per second. Every Twilio response carries a Twilio-Concurrent-Requests header showing the current in-flight count — you can see the ceiling approaching before you hit it. Error 20429 means the request was never processed, so retrying is always safe. The fix is a semaphore or bounded queue, not a longer backoff.

The retry trap. Every snippet on this site for OpenAI, Anthropic, Stripe, GitHub and S3 is "wait N seconds, then retry." On Twilio that is the wrong fix. If your worker pool holds 150 connections open, waiting 2 seconds and retrying still holds 150 connections open. The only fix is to cap concurrency — a semaphore or a bounded queue — so at most 90 or so requests are ever in flight.

SMS throughput by sender type

Twilio's SMS delivery rate is governed by the sender, not by the REST API concurrency limit. A US long code delivers about 1 message segment per second unverified and up to roughly 75 MPS at a high trust score. A toll-free number delivers ~3 MPS before verification and up to 100 after TFNV verification. A short code starts at 100 MPS. Exceeding the sender's rate does not return 429 — Twilio queues and delivers at the permitted rate.

What a 429 / 20429 actually returns

A Twilio 429 returns a JSON body with code: 20429, message: "Too Many Requests", a more_info link, and a Retry-After header. Some endpoints (notably Cohorts) return an RFC 9457 Problem Details body instead, with title, status, and detail fields. Branch on the Twilio code field — the HTTP status alone is shared by every 4xx and 5xx and cannot distinguish a rate limit from a permission error.

HTTP/1.1 429 Too Many Requests
Content-Type: application/json
Twilio-Concurrent-Requests: 100
Retry-After: 1

Retry logic that actually fixes the problem

The correct retry behaviour on Twilio is a concurrency cap, not a backoff. A semaphore limiting simultaneous requests to around 90 keeps you under the 100-request ceiling permanently. Backoff is a politeness layer on top of that — without the cap, backoff converts a one-second throttle into a multi-minute retry storm. The retry loop must also never retry 51202 or 60245, which are hard throttles that retrying cannot fix.

import asyncio, random, httpx

SEM = asyncio.Semaphore(90)

async def twilio_call(client, method, url, headers, **kw):
    async with SEM:
        for attempt in range(5):
            r = await client.request(method, url, headers=headers, **kw)

            if r.status_code != 429:
                r.raise_for_status()
                return r.json()

            body = r.json() if r.content else {}
            code = body.get("code")

            if code in (51202, 60245):
                raise RuntimeError(f"hard throttle: {code} — reduce connections, not retries")

            ra = r.headers.get("retry-after")
            wait = float(ra) if ra else min(30, 2 ** attempt) + random.random()
            await asyncio.sleep(wait)

        raise RuntimeError("retries exhausted")

One escape hatch

Twilio is the only API on this site where a leading indicator exists: Twilio-Concurrent-Requests. Read it on every response. If it climbs past 80, stop opening new connections until it falls — you have roughly 20 requests of headroom before 20429. This is the only page where you can see the ceiling approaching before you hit it, instead of only learning about it from the 429. Pair that with a bounded worker pool and the concurrency limit stops being a surprise.
