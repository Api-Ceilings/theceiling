GitHub returns 403 for both permission errors and rate limits. The headers tell you which one you actually hit — and retrying the wrong one can get your integration banned.

Which 403 do you have?

GitHub returns HTTP 403 for two different conditions: a rate limit and a permission error. A rate limit has either a retry-after header, or x-ratelimit-remaining: 0, or an error message mentioning a rate limit. A 403 with none of those three signals is a permission problem — retrying it wastes calls and can get the integration banned. Branch on the headers before you branch on the status code.

The expensive one. A 403 with no retry-after, no x-ratelimit-remaining: 0, and no rate-limit language in the body is a permission problem. Retrying it wastes calls and, per GitHub's own docs, "continuing to make requests while you are rate limited may result in the banning of your integration."

Primary limits (requests per hour)

GitHub's REST API allows 5,000 requests per hour for authenticated PATs, 60 per hour unauthenticated, and 1,000 per hour per repository for the GITHUB_TOKEN in Actions. GitHub App installations get 5,000 per hour plus 50 per repository and 50 per user above 20, while installations on Enterprise Cloud organisations get 10,000 per hour. The REST and GraphQL APIs have separate primary budgets — exhausting one does not exhaust the other.

Secondary limits (burst protection)

Secondary rate limits protect against bursts and abuse, and none of them can be measured from the response. Concurrency is capped at 100 shared across REST and GraphQL. REST points are capped at 900 per minute, GraphQL at 2,000 per minute. Content-generating requests are capped at 80 per minute and 500 per hour, OAuth token requests at 2,000 per hour, and CPU time at 90 seconds per 60 seconds of real time. GitHub's docs state these limits can change without notice and there is no way to check how close you are to them.

What a rate-limited response looks like

A primary rate limit returns HTTP 403 with x-ratelimit-remaining: 0 and a x-ratelimit-reset epoch timestamp. A secondary limit also returns 403 or 429, but the body mentions "secondary rate limit" or "abuse detection mechanism" and retry-after may or may not be present. The x-ratelimit-remaining header is often non-zero during a secondary limit, which is why checking it first matters — a non-zero remaining with a rate-limit message means secondary, not primary.

HTTP/1.1 403 Forbidden
x-ratelimit-limit: 5000
x-ratelimit-remaining: 0
x-ratelimit-used: 5000
x-ratelimit-reset: 1770000000
x-ratelimit-resource: core

Retry logic that does not get you banned

GitHub's own guidance is to honour retry-after first, then x-ratelimit-reset if remaining is 0, and otherwise wait at least 60 seconds with exponential backoff. Continuing to call while rate limited can get the integration banned. The optimal retry loop returns None for a permission 403 — meaning "do not retry, fix the token" — and only sleeps for genuine rate-limit responses.

import time, random, httpx

def github_wait_seconds(r, attempt):
    if r.status_code not in (403, 429):
        return None

    ra = r.headers.get("retry-after")
    if ra:
        return float(ra)

    if r.headers.get("x-ratelimit-remaining") == "0":
        reset = int(r.headers.get("x-ratelimit-reset", "0"))
        return max(reset - int(time.time()), 0)

    body = r.json() if r.content else {}
    msg = body.get("message", "").lower()
    if r.status_code == 429 or "rate limit" in msg or "abuse" in msg:
        return 60 * (2 ** attempt) + random.random()

    # 403 with no rate-limit signal: permission error. Do not retry.
    return None

One escape hatch

Conditional requests are the only technique on this page that makes a request free. Send If-None-Match with the stored ETag, or If-Modified-Since with Last-Modified. If the resource is unchanged, GitHub returns 304 Not Modified, and a 304 does not count against your primary rate limit. A polling job that touches 1,000 resources hourly costs 1,000 requests the first time and close to 0 after that. Combine with webhooks for anything event-driven, and the primary limit stops being the constraint.
