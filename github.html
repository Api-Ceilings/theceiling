GitHub returns 403 for both permission errors and rate limits. The headers tell you which one you actually hit — and retrying the wrong one can get your integration banned.

Which 403 do you have?

StatusSignalMeaningWhat to do
429Any Rate limited Follow retry-after, or wait for reset
403retry-after present Secondary rate limit Wait exactly that many seconds
403x-ratelimit-remaining: 0 Primary rate limit exhausted Wait until x-ratelimit-reset (UTC epoch)
403Message contains "rate limit" or "abuse detection" Secondary limit, no retry header Wait at least 60s, then exponential backoff
403None of the above Permission error — not a rate limit Do not retry. Fix the token or scopes.
The expensive one. A 403 with no retry-after, no x-ratelimit-remaining: 0, and no rate-limit language in the body is a permission problem. Retrying it wastes calls and, per GitHub's own docs, "continuing to make requests while you are rate limited may result in the banning of your integration." Branch on the headers before you branch on the status code.

The REST and GraphQL APIs have separate primary budgets. Exhausting one does not exhaust the other.

You cannot measure these. GitHub's docs say secondary limits "are subject to change without notice" and there is "no way to check how close you are to them." Every other limit on this page has a header you can read. These do not.

Cost is by nodes requested, not by query. A query for 100 issues each with 10 labels costs 100 × (1 + 10) = 1,100 points. The ceiling for any single query is 500,000 points, and the hourly rate limit cannot exceed 12,500 points.

What a rate-limited response looks like

HTTP/1.1 403 Forbidden
x-ratelimit-limit: 5000
x-ratelimit-remaining: 0
x-ratelimit-used: 5000
x-ratelimit-reset: 1770000000
x-ratelimit-resource: core

{
  "message": "API rate limit exceeded for user ID 12345.",
  "documentation_url": "https://docs.github.com/rest/overview/rate-limits-for-the-rest-api"
}

A secondary limit looks different: status 403 or 429, body mentioning secondary rate limit or abuse detection mechanism, and retry-after may or may not be present. The x-ratelimit-remaining header is often non-zero in that case, which is why checking it first matters.

Retry logic that does not get you banned

import time, random, httpx

def github_wait_seconds(r, attempt):
    if r.status_code not in (403, 429):
        return None

    ra = r.headers.get("retry-after")
    if ra:
        return float(ra)

    if r.headers.get("x-ratelimit-remaining") == "0":
        reset = int(r.headers.get("x-ratelimit-reset", "0"))
        return max(reset - int(time.time()), 0)

    body = r.json() if r.content else {}
    msg = body.get("message", "").lower()
    if r.status_code == 429 or "rate limit" in msg or "abuse" in msg:
        return 60 * (2 ** attempt) + random.random()

    # 403 with no rate-limit signal: permission error. Do not retry.
    return None

def call(method, url, headers, max_retries=4, **kw):
    for attempt in range(max_retries):
        r = httpx.request(method, url, headers=headers, timeout=30, **kw)
        wait = github_wait_seconds(r, attempt)
        if wait is None:
            r.raise_for_status()
            return r.json()
        time.sleep(wait)
    raise RuntimeError("retries exhausted")

GitHub's own guidance: honour retry-after first; then x-ratelimit-reset if remaining is 0; otherwise wait at least 60 seconds and back off exponentially. Continuing to call while rate limited can get the integration banned.

One escape hatch

Conditional requests. GitHub is the only API on this site where a request can be free. Send If-None-Match with the stored ETag (or If-Modified-Since with Last-Modified). If the resource is unchanged, GitHub returns 304 Not Modified — and a 304 does not count against your primary rate limit. A polling job that touches 1,000 resources hourly costs 1,000 requests the first time and close to 0 after that. Combine with webhooks for anything event-driven, and the primary limit stops being the constraint.
