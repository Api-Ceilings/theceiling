S3 is the one API on this site without a fixed ceiling. The limit is per prefix, the third number is unlimited, and the error is a 503 SlowDown that carries no Retry-After header to read.

What a 503 SlowDown actually is

S3 returns 503 SlowDown when traffic to one key-range partition exceeds what that partition can serve while S3 repartitions in the background. It is a scaling signal, not a fixed quota being exhausted. During a sudden spike, 503s continue until the repartitioning finishes, which can take minutes to tens of minutes. No Retry-After header is sent on any S3 throttle — the only valid retry strategy is exponential backoff with jitter.

The one that costs you an outage. S3 returns no Retry-After header on any of these. A retry loop written for OpenAI, Anthropic, Stripe, or GitHub — all of which do send one — will fall through to its fallback path on every S3 throttle. If that fallback is a fixed sleep, you convert a 30-second scaling event into a multi-minute outage.

Rate limits by scope

S3's baseline is at least 3,500 write or 5,500 read requests per second per partitioned prefix, with no limit on the number of prefixes. Because prefixes can be created freely, ten prefixes on a read-heavy workload can reach roughly 55,000 reads per second. 403 AccessDenied responses do not consume the per-prefix TPS quota. AWS states that scaling "happens gradually and is not instantaneous."

The two adjacent throttles people blame on S3

Two throttles are commonly misdiagnosed as S3 rate limits: SSE-KMS encryption and Lambda fan-out. With SSE-KMS, every S3 request adds a KMS call, and KMS has its own per-region requests-per-second quota — KMS throttling surfaces as errors on S3 operations. Lambda-driven fan-out can throttle on the Lambda side and produce retry storms that then trip S3. Check KMS first, then key distribution, then arrival pattern before tuning prefixes.

What a 503 SlowDown returns

A 503 SlowDown response is XML, not JSON, and contains no Retry-After header. The body contains SlowDown, a message asking you to reduce request rate, a RequestId, and a HostId. A retry loop that calls r.json() before checking the status code will throw a parse error and mask the actual throttle.

HTTP/1.1 503 Service Unavailable
Content-Type: application/xml

<?xml version="1.0" encoding="UTF-8"?>
<Error>
  <Code>SlowDown</Code>
  <Message>Please reduce your request rate.</Message>
  <RequestId>CF987P0N12AMKLF2</RequestId>
  <HostId>bjNIzMczkVTroLcdZIWikNDzBckC175HQ+450uHcaFEYnSYxgx76dp3Ob+...</HostId>
</Error>

Retry logic that survives a scaling event

The AWS SDKs default to 3 total attempts (one initial request plus two retries) with exponential backoff and jitter. AWS recommends re-resolving DNS and opening a fresh connection on each retry. For large or variable-size requests over roughly 128 MB, AWS also recommends tracking achieved throughput and proactively retrying the slowest 5 percent of requests, not just the failed ones.

import time, random, httpx

def s3_call(method, url, headers, body=None, max_attempts=3):
    for attempt in range(max_attempts):
        r = httpx.request(method, url, headers=headers, content=body, timeout=60)

        if r.status_code < 300:
            return r

        if r.status_code not in (500, 503):
            r.raise_for_status()

        wait = min(30, (2 ** attempt)) + random.uniform(0, 1)
        time.sleep(wait)

    raise RuntimeError(f"retries exhausted: {r.status_code} {r.text[:200]}")

One escape hatch

There is no support ticket that raises S3's ceiling, because there is no ceiling to raise. The durable fix is prefix distribution: write to many key prefixes so S3 has already split the key space before the spike arrives, and ramp traffic up instead of jumping from zero to peak. The classic self-inflicted wound is sequential naming where every write lands on the same partition edge. At tens of thousands of requests per second against one narrow key range, partition pressure is real.
