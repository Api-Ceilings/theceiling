S3 is the one API on this site without a fixed ceiling. The limit is per prefix, the third number is unlimited, and the error is a 503 SlowDown that carries no Retry-After header to read.

What a 503 SlowDown actually is

StatusError codeRetry-AfterMeaningWhat to do
503SlowDownNone You outran a partition's rate while S3 repartitions Exponential backoff with jitter. Scaling takes minutes, not seconds.
503ServiceUnavailableNone Transient service-side unavailability Backoff and retry
500InternalErrorNone Transient internal failure Backoff and retry
403AccessDeniedNone Permission problem — not a rate limit Fix IAM policy. This does not consume TPS quota.
403SlowDownNone Occasionally returned instead of 503 Treat exactly as a 503 SlowDown
The one that costs you an outage. S3 returns no Retry-After header on any of these. A retry loop written for OpenAI, Anthropic, Stripe, or GitHub — all of which do send one — will fall through to its fallback path on every S3 throttle. If that fallback is a fixed sleep, you convert a 30-second scaling event into a multi-minute outage.

The two adjacent throttles people blame on S3

ThrottleWhere it actually livesHow it surfaces
SSE-KMS encrypted objectsKMS per-region requests/sec quotaKMS throttling appears as errors on your S3 operations. Rule it out before tuning prefixes.
Lambda-driven fan-outLambda concurrency limitsLambda throttles → retry storm → retry storm trips S3. Two throttles, one symptom.
Check the order matters. If your objects use SSE-KMS, no amount of prefix rebalancing will fix a KMS quota problem. Confirm KMS first, then key distribution, then arrival pattern — sudden spikes (a backfill, a cache flush, a new batch job) trigger SlowDown; steady load at the same volume usually does not.

What a 503 SlowDown returns

HTTP/1.1 503 Service Unavailable
Content-Type: application/xml

<?xml version="1.0" encoding="UTF-8"?>
<Error>
  <Code>SlowDown</Code>
  <Message>Please reduce your request rate.</Message>
  <RequestId>CF987P0N12AMKLF2</RequestId>
  <HostId>bjNIzMczkVTroLcdZIWikNDzBckC175HQ+450uHcaFEYnSYxgx76dp3Ob+...</HostId>
</Error>

Note the absence of a Retry-After header. The response body is XML, not JSON — a retry loop that calls r.json() before checking the status code will throw a parse error and mask the actual throttle.

Retry logic that survives a scaling event

import time, random, httpx

def s3_call(method, url, headers, body=None, max_attempts=3):
    for attempt in range(max_attempts):
        r = httpx.request(method, url, headers=headers, content=body, timeout=60)

        if r.status_code < 300:
            return r

        # Only retry the transient classes. Never retry 403.
        if r.status_code not in (500, 503):
            r.raise_for_status()

        # 503 SlowDown carries no Retry-After. Back off with jitter.
        wait = min(30, (2 ** attempt)) + random.uniform(0, 1)
        time.sleep(wait)

        # Fresh connection + DNS lookup on retry (AWS recommendation).
        headers = {**headers}

    raise RuntimeError(f"retries exhausted: {r.status_code} {r.text[:200]}")

AWS SDK default is 3 total attempts (one initial + two retries), using exponential backoff with jitter. For large or variable-size requests (over ~128 MB), AWS also recommends tracking achieved throughput and proactively retrying the slowest 5 percent of requests, not just the failed ones.

One escape hatch

Spread the keys, ramp the rate. There is no support ticket that raises S3's ceiling, because there is no ceiling to raise. The durable fix is prefix distribution: write to many key prefixes so S3 has already split the key space before the spike arrives, and ramp traffic up instead of jumping from zero to peak. The classic self-inflicted wound is sequential naming — logs/2026-11-11-00-00-01.gz, -02.gz, -03.gz — where every write lands on the same partition edge. Modern S3 handles date-based naming far better than it did years ago, so hash-prefixing is no longer general advice, but at tens of thousands of requests per second against one narrow key range the partition pressure is still real.
