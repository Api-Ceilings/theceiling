Firestore Rate Limits: RESOURCE_EXHAUSTED Has 2 Meanings

50,000·20,000·1
reads/day free tier · writes/day free tier · writes/sec per document (soft)
Last verified: 2026-11-28

Firestore is the only API on this site that doesn't return 429. It returns RESOURCE_EXHAUSTED — and the same error code covers two completely different problems with two completely different fixes.

Which RESOURCE_EXHAUSTED do you have?

Firestore returns two distinct RESOURCE_EXHAUSTED errors with the same gRPC status code. The message body tells you which one: "per-user quota" means the daily free tier quota is exhausted and will reset at midnight Pacific. "daily quota or the ramp up limit for writes" means a write-rate scaling limit, which clears in seconds to minutes as Firestore repartitions. Treating both with the same retry loop is the most common Firestore bug.

The two-in-one trap. A retry loop that backs off 60 seconds on every RESOURCE_EXHAUSTED will work for the ramp-up limit but waste 60 seconds on a daily quota that won't clear for hours. Branch on the message string, not the status code. The daily quota's fix is "wait until midnight Pacific or enable billing" — which is a different code path, not a longer sleep.

Free tier quota (resets midnight Pacific)

The Firestore free Spark plan allows 1 GiB stored data, 50,000 document reads per day, 20,000 document writes per day, 20,000 document deletes per day, and 10 GiB outbound data transfer per month. Quotas reset around midnight Pacific time, not on a rolling window. Exceeding any of these returns RESOURCE_EXHAUSTED until the reset or until billing is enabled on the project.

The hidden ceiling — hot-spots and ramp-up

Firestore doesn't publish a writes-per-second ceiling because the real limit is per key-range, not per database. A new collection starts with a modest write budget and scales as Firestore splits key ranges — but only if traffic is distributed across ranges. Sequential document IDs (timestamps, auto-increment counters) land every write on the same range, which is a hot-spot. The 500-writes-per-second-per-document soft limit is separate: sustained updates to one document return ABORTED, not RESOURCE_EXHAUSTED.

Index and request limits (not rate limits — but they fail the same way)

Without billing, a Firestore database allows 200 composite indexes and 200 single-field index configurations; with billing, 1,000 of each. Each document supports up to 40,000 index entries. Each composite index can contain up to 100 fields, and each index entry can be up to 7.5 KiB. A document can have at most 500 field transformations in a single commit or transaction. These are hard limits, not quotas — they don't reset.

What RESOURCE_EXHAUSTED actually looks like

A Firestore RESOURCE_EXHAUSTED carries a gRPC status code and a message string, not a JSON error body like Stripe or OpenAI. The message is the diagnostic. Two variants: "Some resource has been exhausted, perhaps a per-user quota" (daily quota) and "This database has exceeded their daily quota or the ramp up limit for writes, please retry with exponential backoff" (write ramp-up). The second message tells you the fix in the error itself.

# Variant 1 — daily quota (resets midnight Pacific)
{
  "code": 8,
  "message": "Some resource has been exhausted, perhaps a per-user quota.",
  "details": []
}

# Variant 2 — write ramp-up (clears in seconds to minutes)
{
  "code": 8,
  "message": "This database has exceeded their daily quota or the ramp up limit for writes, please retry with exponential backoff.",
  "details": []
}

Retry logic that branches on the message

The correct retry loop parses the message string, not the status code. A "per-user quota" message means the daily free tier is exhausted — log it, alert, wait for midnight Pacific, do not retry. A "ramp up limit" message means the write-rate is scaling — retry with exponential backoff, and check for hot-spots in the data model. A retry loop that treats both the same way either wastes hours or hammers a wall.

import time, random
from google.api_core import exceptions

def firestore_call(fn, max_retries=5):
    for attempt in range(max_retries):
        try:
            return fn()
        except exceptions.ResourceExhausted as e:
            msg = str(e).lower()

            if "per-user quota" in msg:
                # Daily quota — do not retry, alert instead.
                raise SystemExit(
                    "Firestore daily quota exhausted. "
                    "Resets midnight Pacific, or enable billing."
                )

            if "ramp up limit" in msg:
                # Write-rate scaling — backoff and retry.
                wait = min(60, 2 ** attempt) + random.random()
                time.sleep(wait)
                continue

            # Unknown RESOURCE_EXHAUSTED — back off cautiously.
            time.sleep(5 * (attempt + 1))

    raise RuntimeError("retries exhausted")

One escape hatch

Distribute the key space before you need to. Firestore scales by splitting key ranges, but only when traffic is spread across ranges. Use autogenerated IDs (20-character random) or UUIDv4 for high-write collections. Shard any counter across 10+ documents. Keep document writes under roughly 1 per second per document to avoid ABORTED. The classic self-inflicted wound is a timestamped ID that looks clean in logs and concentrates every write on one partition — which works perfectly at 100 writes/day and fails silently at 100,000.
