SendGrid is the only API on this site that publishes no numeric limit table at all. The API ceiling is 10,000 requests per second — but the ceiling that stops most senders is the daily volume a new IP is allowed to send while ISPs build reputation.

Which 429 do you have?

SendGrid returns 429 when the fixed quota for that specific endpoint is exhausted for the current refresh period. The response carries X-RateLimit-Limit, X-RateLimit-Remaining: 0, and an epoch-seconds X-RateLimit-Reset. A 413 is a payload over 30 MB and will never succeed on retry. A 400 with recipient errors means more than 1,000 recipients in one email — split the personalizations, do not back off.

The one that never clears. A 413 will fail identically on every retry because the payload is too large, not because the rate is too high. A retry loop that treats every 4xx as transient converts a one-line attachment fix into an infinite loop. Check the status code before you check the rate-limit headers.

What SendGrid actually publishes

SendGrid publishes no per-endpoint or per-account numeric rate-limit table. The official page documents the header mechanism, the 429 response, and the fact that each endpoint has a fixed quota per refresh period — but not what the quota is. The one official numeric exception is v3 Mail Send: up to 10,000 requests per second, up to 1,000 recipients per email, and a 30 MB total message size. Everything else must be read from the headers at runtime.

The real ceiling — IP warm-up

The API's 10,000 requests per second is not the limit that stops most senders. The limit that stops them is the daily volume a new dedicated IP is allowed to send while ISPs build reputation. SendGrid's guide starts at 50 emails on day 1, 100 on day 2, and 500 on day 3. Warming can last up to 60 days, most clients finish in 30, and some finish in 1–2 weeks. A dedicated IP is only recommended above 50,000 emails per month.

The 30-day rule. Most reputation systems only store 30 days of data. An IP that goes 30 days without sending must be warmed up again. This is why a "seasonal" sending pattern is more expensive than a steady one: the second season starts from cold, not from where the first season ended.
  • Shared IP — no individual warm-up; the shared pool's reputation is the constraint.
  • Dedicated IP — recommended above 50,000 emails/month; Pro and Premier plans can add up to 3 IPs.
  • Warm-up duration — up to 60 days officially; majority within 30; some in 1–2 weeks. A 4–6 week window is a common planning assumption.
  • Separate streams — SendGrid recommends at least two dedicated IPs: one for marketing, one for transactional.

What a 429 actually returns

A SendGrid 429 returns an errors array with the message "too many requests" and the three rate-limit headers. X-RateLimit-Reset is epoch seconds — an absolute timestamp, not a duration. The most common retry bug is treating 1392815263 as "wait 1,392,815,263 seconds" instead of "wait until that date." Read it as reset - now, not as the number itself.

HTTP/1.1 429 TOO MANY REQUESTS
Content-Type: application/json
X-RateLimit-Limit: 150
X-RateLimit-Remaining: 0
X-RateLimit-Reset: 1392815263

{
  "errors": [
    {
      "field": null,
      "message": "too many requests"
    }
  ]
}

Retry logic that respects the reset timestamp

The correct retry waits until X-RateLimit-Reset as an absolute epoch time, not for a fixed backoff. If Retry-After is present, honour it first. If neither header exists, fall back to capped exponential backoff. For v3 Mail Send, batch up to 1,000 recipients per request through personalizations before retrying — a queue with a fixed worker count is the structural fix, because retrying alone does not raise the endpoint quota.

import time, httpx

def sendgrid_call(method, url, headers, max_retries=5, **kw):
    for attempt in range(max_retries):
        r = httpx.request(method, url, headers=headers, timeout=60, **kw)

        if r.status_code != 429:
            r.raise_for_status()
            return r.json()

        retry_after = r.headers.get("retry-after")
        reset = r.headers.get("x-ratelimit-reset")

        if retry_after:
            time.sleep(float(retry_after))
        elif reset:
            wait = max(int(reset) - int(time.time()), 0)
            time.sleep(min(wait, 3600))
        else:
            time.sleep(min(60, 2 ** attempt))

    raise RuntimeError("retries exhausted")

One escape hatch

The durable fix is to treat the API as a queue, not as a synchronous call. Batch recipients through personalizations up to 1,000 per request, separate marketing and transactional traffic onto different IPs, and plan capacity against the warm-up schedule rather than the 10,000 requests per second ceiling. If you need more than the warm-up allows, the answer is more IPs and more days — not a support ticket for a higher API limit.
