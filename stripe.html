Stripe limits you on five different axes and returns the same 429 for all of them. The header most retry loops never read tells you which one you actually hit.

Which 429 do you have?

Stripe returns five different 429s, distinguished by the Stripe-Rate-Limited-Reason response header. Values are global-rate, endpoint-rate, global-concurrency, endpoint-concurrency, or resource-specific. If a 429 arrives without that header, it did not come from a rate limiter — it is usually a lock timeout, and treating it as a rate limit wastes your retry budget.

The expensive one. A 429 with no Stripe-Rate-Limited-Reason header is not a rate limit at all. Any retry loop that treats all 429s the same will back off on a lock timeout (which should be retried quickly) and will fail to slow down on a global-concurrency 429 (which needs fewer simultaneous requests, not a longer wait).

Rate limits by scope

Stripe's global API limit is 100 requests per second per account in live mode and 25 in test mode. Most individual API endpoints allow 25 requests per second, counted in addition to the global limit. A default global concurrency limit of 50 in-progress requests also applies to standard live-mode traffic. Higher limits are available on request through Stripe Support.

What a 429 actually returns

A Stripe 429 carries a Stripe-Rate-Limited-Reason header, a Retry-After header giving seconds to wait, and a rate_limit_error body. The header is the entire diagnostic — it tells you which of the five limits you hit. A 429 without the header is a lock timeout that should be retried quickly, not a rate limit that should be backed off.

HTTP/1.1 429 Too Many Requests
Stripe-Rate-Limited-Reason: global-rate
Retry-After: 2

{
  "error": {
    "type": "rate_limit_error",
    "message": "Too many requests hit the API too quickly. We recommend
                an exponential backoff of your requests."
  }
}

Retry logic that does not hammer the wall

Stripe recommends exponential backoff starting at 1,000 ms, doubling, capping at 32,000 ms, with a maximum of 5 attempts and jitter added. The optimal retry loop branches on Stripe-Rate-Limited-Reason: retry a no-header 429 immediately (lock timeout), reduce concurrency on global-concurrency and endpoint-concurrency, and honour Retry-After on the rest.

import time, random, httpx

def call(method, url, headers, max_retries=5, **kw):
    for attempt in range(max_retries):
        r = httpx.request(method, url, headers=headers, timeout=60, **kw)
        if r.status_code != 429:
            r.raise_for_status()
            return r.json()

        reason = r.headers.get("Stripe-Rate-Limited-Reason")
        ra = r.headers.get("retry-after")

        if reason is None:
            time.sleep(0.5 + random.random())
            continue

        if ra:
            time.sleep(float(ra))
            continue

        wait = min(32, 2 ** attempt) + random.random()
        time.sleep(wait)

    raise RuntimeError("retries exhausted")

One escape hatch

Every rate-limited call is an opportunity to ask whether it needed to be synchronous. Stripe's own recommendation for analytics and migration workloads is to control the request rate on the client, not to raise it on the server. If you find yourself hitting global-rate at 100/s, the answer is usually batching or a queue — not a support ticket. For genuinely high-traffic products, Stripe raises limits on request; for the rest, the fix is on your side of the wire.
