Last verified: 2026-11-11

Discord is the first API on this site where the retry is the failure. A 429 counts as an invalid request, and 10,000 of them in 10 minutes gets your IP banned by Cloudflare — after which every call returns an HTML error page instead of JSON.

Three failure modes, three different fixes

Discord returns three different 429s distinguished by the X-RateLimit-Scope header, and only two of them count toward the ban threshold. user means one route bucket is exhausted — pause that bucket only. global means the 50 req/sec global limit was hit — pause everything. shared means contention on a resource other apps also hit, and shared 429s are the only ones exempt from the 10,000-invalid-request ban count.

The inversion. Seven pages on this site teach "on 429, wait and retry." On Discord that advice manufactures the ban. A tight retry loop on exhausted buckets generates 429s at machine speed, every one of which is an invalid request. 10,000 in 10 minutes — a sustained 16 to 17 requests per second — and Cloudflare bans the IP. A dead token retried overnight does the same thing with 401s.

The ban arithmetic

Discord counts every 401, 403, and 429 response as an invalid request, and bans the IP at 10,000 within 10 minutes. That threshold is reached at roughly 16–17 sustained requests per second — well under the 50 req/sec global limit, which is why the ban arrives before you think you are anywhere near a ceiling. The ban lasts about 10 minutes, during which every request returns Cloudflare's HTML error 1015 instead of Discord JSON. A retry loop calling r.json() on that HTML throws a parse error and masks the cause.

The headers you have to read, because the ceiling is not published

Discord does not publish per-route bucket sizes, and the docs explicitly say limits should not be hard coded. The only source of truth is the X-RateLimit-Limit header on each response. X-RateLimit-Bucket identifies which routes share a limit, X-RateLimit-Reset-After gives the seconds until reset, and X-RateLimit-Scope appears only on 429s. A single request per route converts an unpublished limit into a locally known one.

What a 429 actually returns — three shapes

All three 429 variants carry a float retry_after in the JSON body with millisecond precision, and a rounded Retry-After header in whole seconds. The body field is the more precise value — 64.57 versus the header's 65. X-RateLimit-Scope and X-RateLimit-Global appear only on 429 responses, and an optional code field appears for resource-specific limits such as 20016 (slowmode).

Buckets and the major parameters

Discord's per-route limits split by major parameters: channel_id, guild_id, and webhook_id plus webhook_token. The same endpoint on two different channels is two independent limits, so exceeding /channels/1234 does not block /channels/9876. Non-major IDs in the path do not split the bucket. Emoji routes are limited per guild and their headers do not follow normal conventions — the returned quota may be inaccurate.

Retry logic that does not get you banned

The correct retry loop tracks the invalid-request budget locally and refuses new work before the 10,000 threshold, rather than waiting to see the ban. Shared-scope 429s must be excluded from that budget. 401 and 403 must never be retried — a dead token never recovers. The X-RateLimit-Bucket header on every response should be cached as a bucket map, because that header is the only definition of the ceiling that exists.

import time, httpx

BUCKETS = {}           # bucket id -> monotonic reset time
INVALID = []           # timestamps of 401/403/429 (shared scope excluded)
SAFE_LIMIT = 9500      # margin under Discord's 10,000 / 10 min

def invalid_count():
    now = time.monotonic()
    while INVALID and now - INVALID[0] > 600:
        INVALID.pop(0)
    return len(INVALID)

def discord_call(client, method, path, token, **kw):
    url = f"https://discord.com/api/v10{path}"

    for attempt in range(4):
        if invalid_count() >= SAFE_LIMIT:
            raise RuntimeError("invalid-request budget nearly exhausted")

        r = client.request(method, url,
                           headers={"Authorization": f"Bot {token}"},
                           timeout=30, **kw)

        if r.status_code < 300:
            b = r.headers.get("x-ratelimit-bucket")
            if b:
                BUCKETS[b] = time.monotonic() + float(
                    r.headers.get("x-ratelimit-reset-after", 0))
            return r

        if r.status_code == 429:
            scope = r.headers.get("x-ratelimit-scope", "user")
            if scope != "shared":
                INVALID.append(time.monotonic())
            body = r.json()
            time.sleep(float(body.get("retry_after", 1)))
            continue

        if r.status_code in (401, 403):
            INVALID.append(time.monotonic())
            r.raise_for_status()

        r.raise_for_status()

    raise RuntimeError("retries exhausted")

One escape hatch

Treat X-RateLimit-Bucket as the definition of the ceiling, because Discord does not publish one. Cache bucket identity to X-RateLimit-Reset-After on every response, and treat the map as the ceiling: a route is safe when its bucket reset has passed and Remaining is above zero. That converts an unpublished limit into a locally known one after a single request per route. The corollary is that route keys must use the real path with real IDs — channel_id splits the bucket, and a wrong key silently paces two unrelated routes as one.
