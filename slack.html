Slack has no single ceiling. Each method carries its own tier, the limit is scoped to one method in one workspace for one app, and since May 2025 the same method can be 50× slower depending on how your app is distributed.

Which 429 do you have?

A Slack 429 blocks one method in one workspace for one app — nothing else. Other methods for the same workspace are unaffected, and the same method for a different workspace is unaffected. The Retry-After header is the full instruction for that one bucket. Message posting carries an additional ~1 message/sec per channel limit, and Events API overflows arrive as an app_rate_limited event rather than a 429.

Web API tiers

Slack Web API methods are grouped into four tiers, measured in requests per minute per method per workspace per app. Tier 1 allows 1 or more, Tier 2 allows 20 or more, Tier 3 allows 50 or more, and Tier 4 allows 100 or more. A special tier applies to methods with unique behaviour such as chat.postMessage. Tiers are the same across every Slack plan. The published tier applies only when you use cursored pagination — a full unpaginated fetch gets a stricter limit.

The 2025 change — one method, three different limits

Since 29 May 2025, conversations.history and conversations.replies are limited to 1 request per minute returning at most 15 objects, for apps distributed outside the Slack Marketplace. Marketplace-approved apps and internal customer-built apps keep Tier 3 — 50+ per minute, up to 1,000 objects. To page a 10,000-message channel, a Marketplace app needs about 10 requests and finishes in about 12 seconds. An unlisted app needs about 667 requests and takes over 11 hours — 3,300× slower on the same method.

What a 429 actually returns

A Slack 429 returns {"ok": false, "error": "ratelimited"} with a Retry-After header containing a number of seconds — not an HTTP date, not an epoch timestamp. Slack sends no separate reset header. Waiting less than the stated seconds fails again. Message posting has a separate per-channel limit of about 1 message/sec, and sustained excess can get the app permanently disabled rather than just 429'd.

HTTP/1.1 429 Too Many Requests
Retry-After: 30
Content-Type: application/json

{
  "ok": false,
  "error": "ratelimited"
}

Retry logic that respects the per-method scope

The correct retry model on Slack is one backoff bucket per (workspace, method) pair, not a global one. Backing off conversations.info should not delay users.list, because Slack does not delay it either. Honour the Retry-After seconds exactly, and fall back to exponential backoff with jitter only when the header is absent. The docs warn that burst numbers are intentionally withheld, so designing to a specific burst capacity is unsafe by design — target 1 request per second per method.

import time, random, httpx

BACKOFF = {}

def slack_call(client, method, token, params=None):
    key = (token, method)
    for attempt in range(4):
        r = client.post(f"https://slack.com/api/{method}",
                        headers={"Authorization": f"Bearer {token}"},
                        data=params or {})

        if r.status_code == 200 and r.json().get("ok"):
            BACKOFF.pop(key, None)
            return r.json()

        if r.status_code == 429:
            wait = float(r.headers.get("retry-after", 1))
            time.sleep(wait)
            continue

        body = r.json() if r.content else {}
        if body.get("error") == "ratelimited":
            wait = BACKOFF.get(key, 1)
            time.sleep(wait + random.random())
            BACKOFF[key] = min(wait * 2, 60)
            continue

        r.raise_for_status()

    raise RuntimeError(f"{method}: retries exhausted")

One escape hatch

No retry strategy can make bulk conversations.history practical under the 2025 limit, because 15 messages per call at 1 call per minute is a hard ceiling. The durable options are three: switch to Events API subscriptions so messages arrive as they happen instead of being polled; scope the read to a single thread with conversations.replies and a tight time window; or apply for Marketplace approval if the app genuinely needs history access. The wrong escape hatch is a tighter retry loop — it converts a slow backfill into a disabled app.
