Slack API Rate Limits

1·20·50·100
Tier 1 · Tier 2 · Tier 3 · Tier 4 — requests/min, per method per workspace per app
Last verified: 2026-11-11

Slack has no single ceiling. Each method carries its own tier, the limit is scoped to one method in one workspace for one app, and since May 2025 the same method can be 50× slower depending on how your app is distributed.

Which 429 do you have?

StatusScope of the blockWhat it meansWhat to do
429This method, this workspace One method's tier is exhausted Wait Retry-After seconds, retry this method only
429Other methods — unaffected Not a global ceiling Keep calling other methods; the token bucket is per method
429Other workspaces — unaffected Per-workspace isolation Same method can continue in a different workspace
429 (posting)This channel ~1 message/sec per channel exceeded Space messages out. Bursts risk the app being permanently disabled.
app_rate_limitedEvents API 30,000 deliveries/hour exceeded — an event, not a 429 Read minute_rate_limited and back off that workspace
The scoping that surprises people. A 429 on conversations.info does not stop users.list for the same workspace, and does not stop conversations.info for a different workspace. Slack's Retry-After is the full instruction for that method in that workspace — not a global cool-down.

All Slack plans receive the same tier for a given method. Each method's reference page lists its tier in the Facts section. Source: docs.slack.dev/apis/web-api/rate-limits, checked 2026-11-11.

The pagination trap. The published tier applies only when you use cursored pagination. If you attempt to fetch a full collection in one call, Slack applies a stricter limit. A users.list with limit=1000 and no cursor is not a Tier 2 request — it is a request against a lower ceiling. Paginate or pay.

The 2025 change — one method, three different limits

Distribution modelTierPer request
Marketplace-approved appTier 3 — 50+/minup to 1,000 objects
Internal customer-built appTier 3 — 50+/minup to 1,000 objects
Unlisted app distributed outside MarketplaceTier 1 — 1/min15 objects

Effective 2025-05-29 for new apps and net-new installations of existing apps. Applies to conversations.history and conversations.replies. Slack's stated reason: "to help keep workspace data secure and prevent bulk data exfiltration by unvetted applications." Source: Slack changelog.

The arithmetic: to page a 10,000-message channel, a Marketplace app needs ~10 requests at 1,000/page and completes in about 12 seconds. An unlisted app needs ~667 requests at 15/page and, at 1 request per minute, takes over 11 hours. Same method, same workspace, same token — 3,300× slower.

Slack will not tell you the burst limit. The docs say burst numbers are withheld "because these numbers are subject to change." The recommended design target is 1 request per second for any given method — anything above that is a grace period Slack can revoke.

What a 429 actually returns

HTTP/1.1 429 Too Many Requests
Retry-After: 30
Content-Type: application/json

{
  "ok": false,
  "error": "ratelimited"
}

Retry-After is a number of seconds, not an HTTP date and not an epoch timestamp. Slack sends no separate reset header. Waiting less than the stated value fails again.

Retry logic that respects the per-method scope

import time, random, httpx

# One bucket per (workspace, method) pair — Slack's actual scope.
BACKOFF = {}

def slack_call(client, method, token, params=None):
    key = (token, method)
    for attempt in range(4):
        r = client.post(f"https://slack.com/api/{method}",
                        headers={"Authorization": f"Bearer {token}"},
                        data=params or {})

        if r.status_code == 200 and r.json().get("ok"):
            BACKOFF.pop(key, None)
            return r.json()

        if r.status_code == 429:
            wait = float(r.headers.get("retry-after", 1))
            time.sleep(wait)
            continue

        body = r.json() if r.content else {}
        if body.get("error") == "ratelimited":
            wait = BACKOFF.get(key, 1)
            time.sleep(wait + random.random())
            BACKOFF[key] = min(wait * 2, 60)
            continue

        r.raise_for_status()

    raise RuntimeError(f"{method}: retries exhausted")

The key is a per-method-per-token bucket, not a global one. Backing off conversations.info should not delay users.list, because Slack does not delay it either.

One escape hatch

Use conversations.history less, not faster. Because the 2025 change caps unlisted apps at 15 messages per call and one call per minute, no retry strategy can make bulk history practical. The durable options are: switch to Events API subscriptions so messages arrive as they happen instead of being polled; scope the read to a single thread with conversations.replies and a tight time window; or apply for Marketplace approval if the app genuinely needs history access. The wrong escape hatch is a tighter retry loop — it converts a slow backfill into a disabled app.
