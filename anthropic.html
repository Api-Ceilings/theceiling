Anthropic limits you on three axes at once and returns three different 429s. Whichever axis runs out first is the one that stops you — and one of those 429s never recovers until the first of next month.

Which 429 do you have?

Anthropic returns three distinct 429s, distinguished by the response body. A plain rate_limit_error with a retry-after header means you exceeded RPM, ITPM, or OTPM. A rate_limit_error with details.error_code: enforced_spend_limit_reached and no retry-after means your monthly spend cap is hit — retrying cannot work until 00:00 UTC on the 1st. A 529 overloaded_error is Anthropic capacity saturation, not your account.

The cache trap — your real ceiling is higher

For most Claude models, cache_read_input_tokens do not count toward ITPM. Only uncached input and cache writes count. A 2,000,000 ITPM limit at an 80% cache hit rate can process roughly 10,000,000 total input tokens per minute, because the cached 8M are excluded. If you are hitting 429 on input while caching is on, the limit you are hitting is uncached input, not total input.

  • input_tokens — counts
  • cache_creation_input_tokens — counts
  • cache_read_input_tokens — does not count

What a 429 actually returns

A normal rate limit 429 includes a retry-after header and a standard rate_limit_error body. A spend-cap 429 adds "details": {"error_code": "enforced_spend_limit_reached"} and omits the header entirely. SDKs retry the spend-cap 429 anyway because they only key on error.type — the same error type as a normal rate limit. Branch on details.error_code first.

Headers worth reading before you are throttled

Every Anthropic response carries remaining-request and remaining-token counts before you hit the wall. anthropic-ratelimit-requests-remaining tracks RPM headroom, anthropic-ratelimit-input-tokens-remaining tracks ITPM, and anthropic-ratelimit-output-tokens-remaining tracks OTPM. Each reset header is an RFC 3339 timestamp. Limiting uses a token bucket, not a fixed window.

  • retry-after — seconds to wait. Earlier retries fail.
  • anthropic-ratelimit-requests-remaining — requests left in the window
  • anthropic-ratelimit-input-tokens-remaining — input tokens left
  • anthropic-ratelimit-output-tokens-remaining — output tokens left
  • anthropic-ratelimit-*-reset — RFC 3339 timestamp of full replenishment

Retry logic that does not hammer the wall

The retry must branch on details.error_code before anything else. A spend-cap 429 has no retry-after and does not clear until the 1st of the next month — retrying it fills the log with failures and can trigger the same error for a full billing cycle. For all other 429s and 529s, honour retry-after when present, fall back to exponential backoff with jitter when it isn't.

import time, random, httpx

def call(payload, headers, max_retries=5):
    for attempt in range(max_retries):
        r = httpx.post("https://api.anthropic.com/v1/messages",
                       json=payload, headers=headers, timeout=60)
        if r.status_code == 200:
            return r.json()

        err = r.json().get("error", {})
        if err.get("details", {}).get("error_code") == "enforced_spend_limit_reached":
            raise SystemExit("Spend cap. Resumes 00:00 UTC on the 1st.")

        ra = r.headers.get("retry-after")
        if ra:
            time.sleep(float(ra))
            continue

        if r.status_code in (429, 500, 529):
            time.sleep(min(60, 2 ** attempt) + random.random())
            continue

        r.raise_for_status()

    raise RuntimeError("retries exhausted")

One escape hatch

Claude is also served through Amazon Bedrock and Google Vertex AI, which are separate capacity pools with separate quotas. A 529 on the direct API often succeeds immediately through Bedrock or Vertex. Wire a single fallback provider behind a flag and Anthropic availability stops being a single point of failure. Priority Tier capacity commitments target 99.5% uptime but draw from the same regular rate limits rather than on top of them.
