What a 429 (and 503) looks like

Two distinct errors matter:

HTTPerror.typeerror.codeWhat it means
429rate_limit_errorslow_downYour request rate increased too quickly — even if you're within RPM/TPM.
503service_unavailable_errorserver_is_overloadedThe requested model is temporarily overloaded.

Example 429 body:

{
  "error": {
    "message": "Rate limit reached for gpt-5.5 in organization org-xxx on requests per min (RPM): Limit 5000, Used 5000, Requested 1.",
    "type": "rate_limit_error",
    "code": "slow_down"
  }
}
Rule of thumb: once your traffic reaches 1 million input TPM, increase it by no more than 50% every 15 minutes. The slow_down error is about rate of increase, not absolute limit. Hitting 4,999 RPM in one second can trigger it even if your ceiling is 5,000 RPM.

Retry logic (Python, with Retry-After)

OpenAI's own docs note that their fallback examples do not inspect Retry-After. This snippet does. It respects the header when present, falls back to exponential backoff with jitter when it isn't, and stops on non-retryable errors.

import time, random
from openai import OpenAI, RateLimitError, InternalServerError

client = OpenAI()

def call_with_retry(prompt, max_attempts=5, max_total_seconds=120):
    start = time.time()
    for attempt in range(max_attempts):
        if time.time() - start > max_total_seconds:
            raise TimeoutError("retry budget exhausted")
        try:
            return client.chat.completions.create(
                model="gpt-5.5",
                messages=[{"role": "user", "content": prompt}],
            )
        except (RateLimitError, InternalServerError) as e:
            if attempt == max_attempts - 1:
                raise
            retry_after = None
            if getattr(e, "response", None) is not None:
                retry_after = e.response.headers.get("retry-after")
            if retry_after:
                wait = float(retry_after)
            else:
                wait = (2 ** attempt) + random.uniform(0, 1)
            time.sleep(wait)

Note: unsuccessful requests still count against your per-minute limit. Continuously resending a request won't help — wait and ramp.

Escape hatch

If you're stuck on 429s with legitimate traffic:

  • Batch API — doesn't count against your synchronous RPM/TPM. Queue limits are based on total input tokens queued for a given model. Ideal for jobs that don't need a real-time response.
  • Reduce max_tokens — your effective TPM is the max of max_tokens and the estimated tokens from your prompt. Set it close to your actual expected output.
  • Upgrade tier — Build → Launch → Grow. Each threshold (spend $5, $100, $500 in total credits) unlocks higher limits automatically.
